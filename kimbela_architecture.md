# Kimbela Architecture & Context Study

This document details the architecture, component layout, and database structure of the **Kimbela** platform, compiled after reviewing the codebase files, configurations, and runtime logs.

---

## 1. Technology Stack & Key Libraries

Kimbela is a Python-based monolithic web application built using **Flask** and configured to scale using asynchronous evented I/O.

*   **Core Framework**: [Flask](https://flask.palletsprojects.com/) (version `3.0.3`)
*   **Database ORM**: [Flask-SQLAlchemy](https://flask-sqlalchemy.readthedocs.io/) / [SQLAlchemy](https://www.sqlalchemy.org/) (handles PostgreSQL, MySQL, and SQLite drivers)
*   **Asynchronous Engine**: [eventlet](https://eventlet.net/) (used via `eventlet.monkey_patch()` at startup)
*   **Real-time Communication**: [Flask-SocketIO](https://flask-socketio.readthedocs.io/)
*   **Background Jobs**: [APScheduler](https://apscheduler.github.io/apscheduler/3.x/) (`BackgroundScheduler` and cron/interval triggers)
*   **Email Services**: [Resend](https://resend.com/) API (configured via custom helper classes)
*   **Media & Uploads**: [Cloudinary](https://cloudinary.com/) (handles user avatar, cover photos, digital assets, and matchmaking image hosting)
*   **Payments Ecosystem**:
    *   **Flutterwave** (used heavily in matchmaking)
    *   **Stripe** (with standard checkout sessions and webhooks)
    *   **Monnify** & **Paystack** (fallback/regional integrations)
*   **Caching**: [Flask-Caching](https://flask-caching.readthedocs.io/) (configured with Redis when `REDIS_URL` is set, falling back to a memory-based SimpleCache)

## 3. Database Schema Overview (`models.py`)

Kimbela has a rich database structure containing **38 tables**. The main models are categorized below:

### A. Core User & Social Models
*   `User`: Represents the platform user. Stores standard authentication details, demographics (city, state, country, DOB), interests, and relationships.
    *   **Domain Constraint**: Users must be **at least 31 years old** to join (enforced in `register()`).
*   `FriendRequest`: Manages pending, accepted, or declined connection invitations.
*   `Post`, `Comment`, `Like`, `Reaction`: Standard social media feed tables.
*   `Notification`: System alerts generated by user activities (friend requests, matchmaking matches, etc.).

### B. Matchmaking Service
*   `MatchmakingPackage`: Configuration for subscription plans (pricing, duration, and feature lists).
*   `MatchmakingRequest`: Represents a premium matching entry. Stores user preferences (min/max age, partner gender, religion, ethnicity, and precise location details: `partner_country`, `partner_state`, `partner_city`).
*   `MatchmakingLike` / `MatchmakingView` / `MatchmakingPayments`: Tracks client interactions, profile visits, and transaction histories for paid matchmaking activations.

### C. Marketplace & Advertising
*   `MarketplaceCategory`: Category hierarchies for services/digital items.
*   `MarketplaceService`: Marketplace item listings published by sellers. Supports digital files (Cloudinary URL hosting, downloads) or local services (availability, contact methods).
*   `MarketplaceSubscription` / `MarketplaceSubscriptionPlan`: Tracks subscriptions that sellers purchase to boost listing rankings.
*   `AdCampaign` / `AdPackage` / `SponsoredAd`: Handles advertising campaigns on the social feed, including tracking metrics (`impressions`, `clicks`, `click_through_rate`).

## 4. Background Tasks (`scheduler.py`)

Kimbela uses `BackgroundScheduler` to run tasks asynchronously. The jobs configured include:

1.  **Campaign Expiry Check** (every 6 hours): Scans active advertisement campaigns, tags expired items, and fires email notices for ones expiring soon.
2.  **Daily Maintenance** (at 2:00 AM): Updates listing statistics, click-through rates, and recalculates search ranking scores.
3.  **Marketplace Subscription Check** (at 10:00 AM): Transitions expired seller subscriptions and issues renewals or downgrades.
4.  **Matchmaking Expiry** (at 11:00 AM): Flags expired premium matchmaking requests.
5.  **Birthday Notifications Check** (at 9:00 AM): Automatically runs a daily scan of user DOBs and alerts connected friends.

## 5. Key Architecture & Performance Observations

Based on our inspection of `app_config.py`, `models.py`, and `app.log.1`, we identified several details to keep in mind when modifying or debugging the project:

### ⚠️ Performance Bottleneck: Request Activity Logging
In [app_config.py](file:///home/uplix/Desktop/kimbela/app_config.py), the `@app.after_request` hook executes a synchronous database write (`ActivityLog`) for every page load and API endpoint request:
```python
@app.after_request
def after_request(response):
    # ...
    with db.engine.begin() as conn:
        conn.execute(ActivityLog.__table__.insert().values(**insert_data))
    return response
```
Because the client's geo-location lookup and database insertion are done synchronously within the main request lifecycle, database latency directly extends the client's page load times. This matches warnings in `app.log.1` (e.g., `Slow request: GET /notifications/count took 14.79 seconds`).

### ⚠️ Overlapping Route Defs
In [user.py](file:///home/uplix/Desktop/kimbela/users/user.py), there are two different view functions registered under the exact same path:
*   Line 2459: `@user.route("/notifications")` -> `def get_notifications()`
*   Line 2768: `@user.route("/notifications")` -> `def notifications()`

While Flask handles this by prioritizing the last registered rule, having multiple endpoints pointing to `/notifications` makes the code harder to maintain and can cause unexpected bugs if Ajax clients expect the response shape of one but get the other.

### ⚠️ AJAX Polling Load
Clients poll `/notifications/count` and `/api/messaging/unread-count` continuously to update badge counters. If not properly cached, each poll query executes SQL operations which explains why notification endpoints figure prominently in the slow-request logs.
